# Operating Doctrine Addendum

This addendum condenses the discussion-thread strategy into repo-native form. It complements `workbench/SENSEMAKING.md`, `SYSTEM_SPEC.md`, the split Technical/Doctrine decks, and the v2 operating-doctrine companion.

## Doctrine

> Master the scarce layer. Borrow model capacity. Own problem shape. Compile discoveries back into the engine.

Do not fight every hard model battle. Foundation models, open GNNs, hosted training, synthetic data tools, and interpretability tooling will keep improving. Exploit them aggressively.

Master the boundary conditions: vector fidelity, persistent graph state, supervector formation, validator residuals, workflow exhaust, and rule compilation.

## Pessimist route

Assume:

- DWG conversion is brittle
- annotations are ambiguous
- sparse features are strong
- rewrite invariance is partial
- validators encode policy
- generic AI commoditizes modeling

Then build:

- conversion fidelity harness
- stable graph/export manifest
- annotation residual reports
- sparse calibrated scorer
- matryoshka retrieval memory
- validator-routed review queue
- rule compiler back into engine

The pessimist route is also the moat route.

## Hybrid reality

GNNs are local machinery. Message passing helps when:

- relations are local
- edge types are meaningful
- object identity is stable
- validators define the target
- recomputation stays L-hop local

GNNs struggle when:

- perception is multimodal
- drawing intent is global
- annotations are ambiguous
- schemas drift by drafter/firm/project
- long-range context matters
- graph construction is the bottleneck

Foundation models help when broad context, multimodal interpretation, generative reasoning, code/research acceleration, and explanation dominate.

Validators decide truth, geometry, policy, risk, and auto-apply boundaries.

Memory compounds recurring cases, customer conventions, prototypes, and learned motifs across work.

## Quality loops

The human loop is not a tax. It is the product surface where expertise becomes labels, memory, validator policy, rule candidates, and customer trust.

A good loop:

```text
useful work -> correction / approval -> validator residual -> memory / rule / label update
```

A bad loop:

```text
abstract labeling -> unclear payoff -> noisy labels -> no system change
```

Engagement is an ML systems variable: better DX creates better labels, better labels create better automation, better automation earns more trust.

## Objective-loop autonomy

The holy grail is not replacing the expert. It is moving the expert up the abstraction ladder while the system loops below them.

| Autonomy mode | What happens | Human role |
|---|---|---|
| Assist | Model suggests one step at a time. | Human decides every step. |
| Co-pilot | Model batches low-risk edits and review groups. | Human reviews grouped changes. |
| Verifier loop | Model searches until validators pass or uncertainty/risk threshold is hit. | Human reviews residual summary and exceptions. |
| Objective loop | Model decomposes goal, edits, verifies, retrieves cases, revises plan, and stops at a risk boundary. | Human approves higher-order objective and irreversible choices. |

## High-reliability vs judgment-in-loop

For each proposed change ask:

- can scope be bounded?
- can required objects be typed?
- do validators cover the risk?
- has this pattern repeated?
- is confidence calibrated?

If yes: high-reliability change -> auto-apply or batch approve.

If no: judgment-in-loop -> route to operator with scoped affordance.

## Building codes and interpretive constraints

Use validators for hard, discrete, externally checkable constraints.

Use embedded scoring for interpretive, preference-like, or context-dependent constraints.

Building codes become computationally powerful only when supervectors and object identity are strong enough that the code predicate has reliable operands. Before that, code automation becomes noisy rule theater.

Validator tiering:

```text
V0: mathematical geometry
closure, winding, containment, duplicate footprint

V1: engineering heuristics
clearance, route cost, accessibility proxy, MEP separation

V2: jurisdiction / firm policy
code versions, office standards, auto-apply thresholds

V3: human review
ambiguous intent, liability-sensitive changes
```

## Dictionary -> geometry -> compiler

Concept dictionary:

```text
wall, hatch, door, label, shaft, dimension
```

Representation geometry:

```text
rewrite orbits, validator residual directions, edit-acceptance manifolds, motif neighborhoods, customer convention basins
```

Compiler loop:

```text
model discovers geometry -> probes inspect it -> validators verify it -> engine compiles it into deterministic rule or supervector
```

The product does not need every concept atom. It needs the geometry that makes edits predictable.

## Company metrics

Track many diagnostics, but steer by four metrics that compose into one chain:

| Metric | Stage | What it measures |
|---|---|---|
| Review yield | Input to loop | Useful labels/preferences per minute of operator time. |
| Correction compression | Immediate value | Manual edit work avoided per accepted suggestion. |
| Rule conversion rate | Compounding output | Fraction of learned motifs promoted into deterministic engine rules. |
| Time-to-trust | Autonomy outcome | Interactions before customer allows a higher autonomy level. |

Everything else — acceptance rate, repeat-error decay, review-band efficiency, residual closure, objective completion — is useful per experiment, but should not become the company steering dashboard too early.
